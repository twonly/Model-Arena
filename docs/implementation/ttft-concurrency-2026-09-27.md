# 六模型并发实测（2026-09-27）

> 以下是发布前的实验。后续上线验收已捕获 UltraSpeed 长等待及厂商耗时回执，最新证据见 [发布记录](./ttft-release-2026-09-27.md)。

## 结论

用户分享 https://www.tokrace.com/zh-CN/r/hMqeqf6gVW 中，UltraSpeed 首 Token 为 **38.712 秒**，随后有效输出窗口约 **0.690 秒**。遥测确认对应 `2026-09-26T08:53:44Z` 上报的同一轮六模型结果，MiMo 接口是 `api.xiaomimimo.com`。

本次真实浏览器在生产站点点击“开始对比”，使用分享内的实际提示与默认参数，完成 **五轮六模型并发，共 30 次成功请求**。前三轮沿用线上路由，后两轮仅在隔离测试浏览器里让六模型都走现有 Cloudflare 通路；没有修改全站配置。

没有复现 UltraSpeed 的 38.7 秒，但确实复现了其他模型的长首响：MiMo Flash 21.355 秒、GLM Flash 14.871 秒。证据不支持“六并发必然耗尽连接”或本站整体串行排队；更符合单个上游请求的长尾延迟。仍不能区分上游网络、厂商调度/账号限制、计算或缓冲，也未取得历史时刻的 CPU/内存证据，不能宣称彻底排除所有服务端资源问题。

## 连接数和本站等待的证据

- CDP 网络记录：前三轮全部使用 HTTP/2。每轮发往本站的四条模型请求复用同一连接；记录的发送启动耗时均小于 0.4 ms，没有等待其他模型释放浏览器连接。
- 第三轮四个 Vercel 请求在客户端约 0.6 ms 内发起，平台接收时间落在 `01:10:28.569–571Z`，跨度 2 ms。MiMo Flash 接收响应头为 21.623 秒，代理首 Token 为 21.355 秒；同轮其他模型已正常出字。
- 原分享 38.712 秒本身由代理内部时钟计算。浏览器发送前的连接排队不会被计入这个值。
- 代码中的并发入口直接启动各模型任务，没有串行队列或每供应商连接数上限；`/api/chat` 的每 IP 每分钟 60 次限制直接返回 429，不是先排队几十秒再放行。本次浏览器 30 次模型请求均 HTTP 200。
- 测试窗口内查询到的 Vercel 日志未出现 error；这不等于已取得 CPU/内存监控，也不能据此回溯证明昨天完全没有过载。历史窗口日志查询失败，未把缺失记录解释为“无故障”。

慢 Flash 的 Vercel 请求 ID：`hnd1::hkg1::h5g9b-1790471428569-1e01109c7a07`。旧生产版本没有回传厂商 completion/request ID，因此此 ID 只能供 Vercel 侧关联，不能替代小米请求 ID。

## 直连对照及失败样本

两组独立直连对照使用同一个配置的 Xiaomi Key：

| UltraSpeed 场景 | 第一组 | 第二组 |
| --- | ---: | ---: |
| 单独直连小米 | 0.917 s | 1.119 s |
| 三个 MiMo 同时直连 | 0.835 s | 2.193 s |

新建连接的 DNS/TCP/TLS 累计完成时间约 0.15–0.22 秒；诊断客户端允许六条 socket，三路直连没有被测试脚本自身的单连接池串行化。两组未复现几十秒首响。

另外跑了 Node 客户端生产通路矩阵：第一轮六请求成功，UltraSpeed 为 1.087 秒；其后部分请求在收到 HTTP 响应头之前发生 `ECONNRESET`，矩阵按设计停止，不自动重试付费请求。两份矩阵总计 10 个请求失败，未混入浏览器成功样本，也未将网络重置误称为模型排队。第一份失败记录未保留底层错误码，第二份已记录 `ECONNRESET`。此时浏览器实测是判断用户实际使用路径的主要证据。

Xiaomi 的 `usage.pd` 原始字段已保存在直连回执中；字段定义未经官方确认，不能把 `recv_ms` 等直接命名为队列时间。

## 下一步和发布边界

[Xiaomi 官方限流说明](https://mimo.mi.com/docs/zh-CN/api/guidance/rate-limit)明确提到账号模型并发上限，以及高负载时可能延迟或返回 429；UltraSpeed 配额属于定制服务。这说明厂商限制是可能原因，不证明本次历史请求触发了它。

当前最有价值的动作是发布已准备的分阶段诊断补丁：捕捉慢请求的代理准备、上游响应头、首字节、首 Token、重试次数和厂商请求 ID，再用实际慢请求回执确认责任段。尚没有证据需要增加连接池、扩容或把六模型改成串行；小样本也不足以认定换 Cloudflare 能修复长尾。

线上仍未包含上一轮诊断补丁。本轮新增并发诊断脚本、修正诊断客户端 socket 上限并保存证据，没有提交、推送、部署或修改全站路由。脚本语法检查、解析器自检、`git diff --check` 通过；本轮没有修改应用运行逻辑。
